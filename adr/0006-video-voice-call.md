# ADR 0006: Видео/голосовая связь между пользователями по ссылке

Статус: принято. Issue #14.

## Контекст
Нужна возможность видео/аудио связи прямо на сайте: пользователь жмёт
кнопку на панели → получает уникальную ссылку → отправляет другу →
оба открывают сайт по этой ссылке и включают камеру кнопкой → видео
друг друга появляется в углу экрана (picture-in-picture), слышат друг
друга. Ссылку может открыть несколько человек (групповой звонок).
Сайт статический (python http.server / GitHub Pages), своего backend
нет — это ограничивает выбор способа сигналинга.

## Решение
- Технология медиа: WebRTC (getUserMedia + RTCPeerConnection), топология
  mesh (каждый с каждым) — достаточно для малых групп друзей (до ~4-6
  участников), SFU/MCU не нужен.
- Сигналинг: библиотека PeerJS с публичным облачным PeerServer
  (0.peerjs.com, бесплатный брокер) — не требует своего сервера,
  совместимо со статическим хостингом. ICE: публичный STUN Google.
  Ограничение: без TURN звонок может не установиться за строгим NAT/
  корпоративным firewall — фиксируем как известное ограничение v1.
- ID звонка = короткий случайный id (nanoid/crypto), кладётся в URL
  как ?call=ID. Открывший ссылку с ?call= видит предложение
  "Присоединиться к звонку".
- Новый модуль js/call.js: кнопки "Позвонить"/"Присоединиться" на
  панели управления, создание/копирование ссылки, PeerJS-подключение,
  локальное и удалённые видео как плавающие DOM-окна в углу экрана
  (свой поверх сцены three.js, не в WebGL), toggle камеры/микрофона,
  кнопка завершения звонка закрывает окна и останавливает треки.
- Стили/DOM выносятся в js/call.js + отдельный call.css (или инлайн
  через JS), логика подключения отделена от UI-рендера окон.

## Уточнения (после ревью #14)
- TURN-сервер сознательно не берём в v1 (риск недоступности за строгим NAT
  фиксируем как известное ограничение).
- Прод — GitHub Pages, доступ только по прямой ссылке ?call=ID, без
  авторизации.
- Изоляция от WebGL-сцены: если звонок будет проседать по производительности
  из-за рендера сцены (three.js), предусмотреть вынос call.js в отдельный
  iframe/отдельную страницу (например call.html), которая грузит только
  PeerJS+видео и общается с основной страницей через postMessage/URL —
  без пересборки в отдельный npm-пакет/деплой. Решение по факту замеров
  в #25, не блокирует первую реализацию (пока — один модуль на той же
  странице).

## Уточнения (после инцидента #25, мобильные сети)
- Облачный 0.peerjs.com оказался ненадёжен: на мобильных операторах
  wss-соединение к нему рвётся сразу (close code 1006), звонок с
  телефона не устанавливается вообще — это основной сценарий
  использования.
- Решение: переходим на свой PeerServer (npm `peer`), задеплоенный
  отдельным процессом на бесплатном хостинге (Render). Сайт остаётся
  статическим (GitHub Pages), меняется только url/port сигналинга в
  `new Peer()`.

## Альтернативы
- Свой сигналинг-сервер (Node/ws) — изначально отклонено для v1, но
  принято после инцидента с мобильными сетями (см. выше).
- SFU (mediasoup/LiveKit) — избыточно для звонков друзей, требует
  сервер и инфраструктуру.
- Встраивание Jitsi Meet через iframe — самый простой вариант, но
  ломает описанный UX (окна в углу поверх сцены, свой минимальный UI)
  и даёт меньше контроля над видом; отклонено.

## Подзадачи (issues)
1. Базовый видеозвонок 1:1 по ссылке: кнопка "Позвонить", генерация и
   копирование ссылки, PeerJS-подключение, окна локального/удалённого
   видео в углу экрана, toggle камеры/микрофона, завершение звонка.
2. Групповой звонок (mesh, несколько человек по одной ссылке).
3. UX устойчивости: статус соединения, отказ доступа к камере/микрофону,
   переподключение при обрыве, аккуратное закрытие окон.
